## Purpose

Определяет, как клиент iOS получает список галочек mokaGram и их изменения от сервера `api.moka.wtf`, какие поля применяет и как переживает обрывы, фон и отсутствие сети.

## ADDED Requirements

### Requirement: Список с API как главный источник
Клиент SHALL запрашивать полный список галочек у `https://api.moka.wtf/v1/badges` и использовать его раньше остальных источников. Если API не ответил или ответил неверным форматом, клиент SHALL перейти к запасным источникам (GitHub, затем `@mokagent`) и не показывать пользователю ошибку.

#### Scenario: API отвечает
- **WHEN** приложение запрашивает список и API возвращает корректный ответ
- **THEN** клиент применяет этот список и не обращается к запасным источникам

#### Scenario: API недоступен
- **WHEN** запрос к API завершился ошибкой, таймаутом или вернул неверный формат
- **THEN** клиент запрашивает следующий источник, а известные галочки остаются на месте

### Requirement: Мгновенные изменения по потоку событий
Пока приложение на переднем плане, клиент SHALL держать открытым поток событий `https://api.moka.wtf/v1/events` и применять каждое событие `granted`, `updated`, `revoked` к одному пользователю, не перезагружая весь список. Изменение SHALL быть видно в уже открытых экранах без перезапуска приложения.

#### Scenario: Выдача галочки
- **WHEN** приходит событие `granted` для пользователя, чей чат виден в списке чатов
- **THEN** у этого пользователя появляется галочка, строка обновляется без действий пользователя

#### Scenario: Снятие галочки
- **WHEN** приходит событие `revoked` для пользователя
- **THEN** галочка пропадает везде, где она была нарисована, и убирается из кэша

#### Scenario: Изменение значка или подписи
- **WHEN** приходит событие `updated` с новым `emojiId` или `signature`
- **THEN** клиент рисует новый значок, а прежний больше не показывает

### Requirement: Догрузка пропущенного и полная пересинхронизация
При обрыве потока клиент SHALL переподключаться с растущей паузой и передавать идентификатор последнего полученного события. Если сервер сообщает `resync = true` в событии `hello`, клиент SHALL заново загрузить весь список.

#### Scenario: Короткий обрыв
- **WHEN** соединение оборвалось, и сервер может досытать пропущенные события
- **THEN** клиент применяет досланные события и не загружает список целиком

#### Scenario: Пропущено слишком много
- **WHEN** после переподключения `hello` содержит `resync = true`
- **THEN** клиент загружает весь список заново и заменяет им известный

### Requirement: Мёртвое соединение обнаруживается
Сервер шлёт служебный `ping` раз в 20 секунд. Если данных нет дольше 60 секунд, клиент SHALL считать соединение мёртвым, закрыть его и открыть заново.

#### Scenario: Смена сети без закрытия сокета
- **WHEN** после смены сети поток молчит больше минуты
- **THEN** клиент переподключается и догоняет изменения

### Requirement: Поток живёт на переднем плане
Клиент SHALL закрывать поток, когда приложение уходит в фон, и при возврате SHALL сначала обновить список, затем снова открыть поток.

#### Scenario: Возврат в приложение
- **WHEN** пользователь возвращается в приложение после паузы
- **THEN** галочки соответствуют текущему списку на сервере, даже если события были пропущены

### Requirement: Данные галочки с сервера
Для каждого пользователя клиент SHALL применять `emojiId` как значок (пусто значит общий значок списка) и `signature` как подпись. Правила выбора значка и синего значка описаны в отдельных требованиях ниже. Поля `tier` и способ оплаты клиент не использует и не показывает.

#### Scenario: Личный значок
- **WHEN** у пользователя в ответе указан свой `emojiId`
- **THEN** вместо общего значка рисуется этот

#### Scenario: Значок по умолчанию
- **WHEN** `emojiId` равен `null`
- **THEN** рисуется общий значок списка (`defaultEmojiId`)

### Requirement: Кэш и офлайн
Клиент SHALL хранить последний принятый список и последнюю принятую версию на устройстве и при запуске показывать галочки из него без ожидания сети. Неверные данные от любого источника или события SHALL NOT удалять уже известные галочки. Кэш предыдущей версии приложения SHALL оставаться читаемым.

#### Scenario: Запуск без сети
- **WHEN** приложение запускается без сети, а кэш есть
- **THEN** галочки из кэша видны сразу

#### Scenario: Испорченное событие
- **WHEN** событие не разобрать или в нём нет пользователя
- **THEN** оно пропускается, остальные события применяются, известные галочки не меняются

### Requirement: Значок в шапке профиля
Клиент SHALL рисовать значок галочки в шапке профиля человека, у которого есть галочка, рядом с его именем, тем же значком, что и в списке чатов. Профиль, который уже открыт, SHALL обновиться без закрытия, когда список или событие меняет галочку этого человека.

#### Scenario: Профиль человека с галочкой
- **WHEN** пользователь открывает профиль человека, у которого есть галочка
- **THEN** в шапке рядом с именем нарисован значок этого человека, и он совпадает со значком в списке чатов

#### Scenario: Список пришёл после открытия профиля
- **WHEN** профиль открыт, а список галочек загрузился или изменился после этого
- **THEN** значок появляется (или пропадает) в открытом профиле без действий пользователя

#### Scenario: Человека без галочки
- **WHEN** открыт профиль человека, которого нет в списке и который не разработчик
- **THEN** значка mokaGram в шапке нет

### Requirement: Подпись галочки
Для каждой галочки клиент SHALL определять подпись по приоритету: роль команды (разработчик), затем подпись с сервера, затем фиксированный текст «Поддерживает mokaGram». У разработчика подпись SHALL быть «Разработчик mokaGram», у владельца «Разработчик и владелец mokaGram». Подпись с сервера SHALL быть обрезана до 64 знаков. Клиент SHALL показывать подпись текстом под основным блоком профиля, а в карточке «о чате» только если это не требует отдельной доработки.

#### Scenario: Подпись с сервера
- **WHEN** у человека с галочкой нет роли команды и сервер прислал подпись
- **THEN** под блоком профиля показан текст этой подписи

#### Scenario: Подписи нет
- **WHEN** у человека с галочкой нет роли команды и нет подписи с сервера
- **THEN** под блоком профиля показан текст «Поддерживает mokaGram»

#### Scenario: Роль сильнее подписи
- **WHEN** человек разработчик, а сервер тоже прислал для него подпись
- **THEN** показана роль («Разработчик mokaGram»), а у владельца «Разработчик и владелец mokaGram»

#### Scenario: Нет галочки
- **WHEN** у человека нет галочки
- **THEN** подпись mokaGram не показывается

#### Scenario: Подпись обновилась
- **WHEN** приходит событие `updated` с новой подписью для человека, чей профиль открыт
- **THEN** текст под блоком профиля меняется без закрытия профиля

### Requirement: Разработчики определяются по id и по имени пользователя
Клиент SHALL считать человека разработчиком, если его числовой id входит в список разработчиков или его имя пользователя (без учёта регистра) входит в список имён: `ecronx`, `xdshkaaa`, `xdshka`, `litteraliy`. Владелец определяется по числовому id `6612638154` или по имени `ecronx`. Данные сервера SHALL NOT снимать значок и роль разработчика.

#### Scenario: Разработчик по имени
- **WHEN** у человека имя пользователя `xdshka` (или другое из списка), а в списке сервера его нет
- **THEN** у него есть галочка с личным значком и подписью разработчика

#### Scenario: Разработчик по id
- **WHEN** id человека равен `6612638154`, а имя пользователя скрыто
- **THEN** у него есть галочка владельца

#### Scenario: Снятие галочки у разработчика
- **WHEN** сервер присылает `revoked` для разработчика
- **THEN** его значок и роль остаются

#### Scenario: Имя сменили
- **WHEN** человек с id не из списка поменял имя пользователя на не из списка и его нет на сервере
- **THEN** у него нет галочки

### Requirement: Синий значок
Клиент SHALL рисовать синий значок (значок владельца) для разработчиков из требования выше, как Desktop, независимо от сервера. Для остальных людей клиент SHALL рисовать синий значок, если сервер пометил галочку как синюю (`blue = true` или id в `blueUserIds`) и указал значок `blueEmojiId`; личный значок сервера у такого человека имеет приоритет. Приоритет значков: клиентский синий разработчика, затем личный значок сервера, затем серверный синий, затем общий значок списка, затем встроенный.

#### Scenario: Синий разработчик
- **WHEN** у разработчика нет личного значка на сервере
- **THEN** рисуется синий значок

#### Scenario: Синяя галочка с сервера
- **WHEN** сервер пометил человека синим, указал `blueEmojiId` и не указал личный значок
- **THEN** рисуется `blueEmojiId`

#### Scenario: Синий без значка в ответе
- **WHEN** сервер пометил человека синим, но `blueEmojiId` не указан
- **THEN** рисуется общий значок списка

#### Scenario: Личный значок сильнее синего
- **WHEN** у синего человека сервер указал личный `emojiId`
- **THEN** рисуется личный значок

### Requirement: Диагностика потока и списка
Клиент SHALL писать в системный журнал события работы с галочками: запрос списка и его результат (источник, версия, число записей), подключение и отключение потока с причиной, каждое событие (тип, версия, id пользователя), обрыв и паузу перед повтором. Журнал SHALL NOT содержать иных данных, кроме id пользователей и версий.

#### Scenario: Отладка по проводу
- **WHEN** приложение запущено с устройства, подключённого к компьютеру
- **THEN** в журнале видно, какой источник дал список, сколько в нём записей, подключён ли поток и пришло ли событие
