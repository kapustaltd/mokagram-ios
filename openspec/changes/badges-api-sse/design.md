## Context

`MokoBadges` (MokoCore) уже держит множество holders в памяти под `NSLock`, кэш в `MokoStorage.defaults` (`moko.badges.cache.v1`, формат `badges.json`), троттлит `refresh()` раз в 60 с, шлёт `changedNotification`, на который перерисовываются `ChatListItemNode` и `ContactsPeerItemNode`. Запускается из `AppDelegate` (`refresh()`) и `ApplicationContext` (`setInlineFallback`, `refresh(force:)`). Читает его `Peer.mokaBadgeIconFileId` в `PeerUtils.swift`.

Контракт сервера (по сообщению бэкендера): `GET /v1/badges` отдаёт `{rev, updatedAt, defaultEmojiId, blueEmojiId, blueUserIds, total, badges:[{userId, tier 1–3, emojiId|null (строка), signature|null, blue, grantedAt}]}`, кэш 30 с, `ETag`. `GET /v1/badges/{userId}`: 404, если нет. `GET /v1/events`: SSE, первым `event: hello` с `{rev, resync}`, затем `event: badge` с `{id, type: granted|updated|revoked, userId, badge|null, at}`; `: ping` каждые 20 с; `id` события равен `rev`; `Last-Event-ID` досылает до 300 событий. Лимит nginx: до 5 SSE-соединений с одного IP. Поведение Desktop-клиента (`mokagram_misc.cpp`, коммит `f8e4dc11`) берётся за образец: API, затем GitHub, затем `@mokagent`; SSE с паузой `min(3000 × сбоев, 30000)` мс; тишина дольше 60 с значит обрыв; при живом потоке периодическая сверка списка раз в 5 минут.

## Goals / Non-Goals

**Goals:**
- Галочка у всех пользователей появляется и пропадает за секунды, без перезапуска.
- Один пользователь на событие: без перезагрузки списка и без полного перерисовывания.
- Существующая цепочка GitHub / `@mokagent` и кэш остаются рабочим запасным путём.

**Non-Goals:**
- Выдача и снятие галочек, оплата, админка (это бот и сервер).
- Фоновые обновления при закрытом приложении (iOS не даёт держать соединение; для этого есть возврат на передний план).
- Показ `tier`.
- Изменения сервера или бота.

## Decisions

- **Состояние: словарь, а не множество.** `users: Set<Int64>` заменяется на `[Int64: Entry]` (`emojiId?`, `signature?`, `blue`), плюс `rev`, `defaultEmojiId`, `blueEmojiId`. Иначе личный значок и подпись некуда положить. `kind(userId:username:)` и `iconFileId` сохраняют сигнатуры, чтобы не трогать места вызова. Альтернатива (второй словарь рядом со множеством) отвергнута: две структуры можно рассинхронизировать на событии.
- **Выбор значка:** личный `emojiId` > для `blue` значок `blueEmojiId` (если задан) > `defaultEmojiId` > встроенный `defaultSubIcon`. Разработчики решаются раньше и от сервера не зависят.
- **Кэш v2 рядом с v1.** Новый ключ хранит исходное тело ответа `/v1/badges` (его же формат разбирается при чтении), а события, применённые после, дописываются в сохранённое состояние. Ключ v1 читается, если v2 нет; при первой успешной записи v2 v1 не удаляется (откат приложения не теряет данные). Парсер принимает оба формата: `{users, emoji_id}` и `{badges, defaultEmojiId}`.
- **SSE на `URLSession.bytes(for:)`** (async), без сторонней библиотеки: разбор блоков по пустой строке, поля `event`, `data`, `id`, комментарии `:` пропускаются, но обновляют время последних данных. Задача отменяется при уходе в фон. Альтернатива (`URLSessionDataDelegate` с буфером) отвергнута как более громоздкая, при том что iOS 15+ давно минимальная цель.
- **События применяются под тем же замком**, `changedNotification` шлётся один раз на пачку событий, а не на каждое (после переподключения может прийти до 300). Идентификатор последнего события хранится в памяти и в кэше; если приходит `hello` с `rev` меньше сохранённого, это считается сбросом сервера и запускается полная загрузка.
- **Жизненный цикл:** `didBecomeActive` → `refresh(force:)` (сначала список по ETag, `If-None-Match`; 304 значит «не менять») → открыть поток; `didEnterBackground` → отменить поток. Это совпадает с тем, как Desktop привязывает поток к работающему клиенту, и укладывается в лимит 5 соединений на IP: фон не держит сокет.
- **Подстраховочная сверка списка раз в 5 минут** при живом потоке (как на Desktop), вместо раз в минуту без потока. `minimumRefreshInterval` остаётся для запасных путей.
- **Подпись.** Поверхность на iOS есть: профиль рисует описание проверки бота комментарием под блоком (`PeerInfoScreenCommentItem` с иконкой в префиксе, `PeerInfoProfileItems.swift:569`) из `CachedUserData.verification` (`PeerVerification{botId, iconFileId, description, descriptionEntities}`). Карточка «о чате» читает тот же `verification` (`ChatControllerContentData.swift:962`, `ChatHistoryEntriesForView.swift:635`, `ChatUserInfoItem.swift:407`). Решение: как Desktop, подставлять синтетический `PeerVerification` (botId = id пользователя, `iconFileId` = значок галочки, `description` = подпись) там, где у человека есть галочка mokaGram; серверная проверка от бота при этом заменяется, как и значок. Подпись выбирается одной функцией в MokoCore: роль → `signature` → «Поддерживает mokaGram»; строки роли и запасная идут через локализацию Moko. Профиль: обязательно. Карточка «о чате»: тот же вход, делается после профиля; если окажется шире профиля, откладывается (записать в задачах).
- **Разработчики.** Сейчас в iOS: владелец по id `6612638154` и имени `ecronx` (значок `5397879498492389616`, он же Desktop `kBlueIcon`), `xdshkaaa` по имени с заглушкой значка `...617` (такого значка может не существовать, тогда рисуется пусто), `xdshka` и `litteraliy` не известны. Нужно: таблица «имя → роль» (`ecronx` владелец; `xdshkaaa`, `xdshka`, `litteraliy` разработчики) плюс таблица id (пока только владелец). Заглушку `...617` убрать: разработчики получают синий значок Desktop, пока не задан собственный. Роль определяет и подпись.
- **Синий значок.** Desktop читает только клиентский синий (`kBlueIcon` для владельца и имён `litteraliy`, `xdshka`) и игнорирует `blue`/`blueEmojiId` из API. Согласование: клиентский синий разработчика > личный `emojiId` > серверный синий (`blueEmojiId`, иначе общий) > `defaultEmojiId` > встроенный. Для не-разработчиков это расходится с Desktop только когда сервер прислал `blue`, что Desktop не показывает; расхождение осознанное и убирается одной строкой, если пользователь решит иначе (см. открытые вопросы).
- **Диагностика причины «в профиле нет значка».** Наблюдено в коде (чтение): шапка профиля (`PeerInfoHeaderNode.swift:612-617, 1081-1086`) читает `peer.verificationIconFileId`, а оно отдаёт значок `MokoBadges` раньше серверного (`PeerUtils.swift:358-366`); значок рисуется слева от имени (`:1673`), так как это не `.verified`. То есть цепочка есть. Предположено (на устройстве не проверено): (1) данные не дошли до `MokoBadges` (список пуст, сеть, ATS, ответ другого формата), в коде нет ни одного лога; (2) тестовый человек не в списке (3 записи) и не распознан как разработчик: `xdshkaaa` без id, `xdshka` вовсе не известен; (3) значок `...617` у `xdshkaaa` пуст; (4) профиль и шапка чата не подписаны на `changedNotification` (`ChatListItem.swift:1793` и `ContactsPeerItem.swift:673` подписаны, профиль и чат нет), поэтому открытый до загрузки экран не обновится; (5) у карточки профиля нет подписи, и значок в шапке мал на фоне цветной шапки. Диагностика (задача 6.1) отделяет данные от рисования логами и отладочным выводом `MokoBadges.iconFileId` для id открытого профиля.
- **Журнал.** `os.Logger` (подсистема приложения, категория `badges`) в MokoCore: id пользователей и версии публичны (`privacy: .public`), без URL с токенами. Тот же текст в `NSLog` не дублируется.

## Risks / Trade-offs

- [Незаархивированное изменение `verification-badges` ещё не имеет основной спеки] → это изменение вводит отдельную capability `badges-api` и ссылается на прежнюю только по смыслу, архивирование идёт в любом порядке.
- [Состояние гонки: событие пришло раньше, чем применён список] → список заменяет состояние целиком только если его `rev` не меньше последнего события; иначе применяется, а затем досылаются события через `Last-Event-ID`.
- [Лимит 5 SSE на IP при нескольких устройствах за одним NAT] → при отказе (429/444/ошибка) пауза растёт до 30 с, а список всё равно обновляется раз в 5 минут и при возврате в приложение.
- [Сервер сейчас без реальных ссылок на источники кроме `badges.json`] → запасной путь GitHub сохраняется; его URL проверить заново (в коде стоит `ecronxy/mokagram`, у Desktop-коммита другой владелец репозитория).
- [`emojiId` строкой не помещается в JSON-число без потерь] → разбор через строку, как делает текущий парсер.
- [Развёртывание] Нет серверных шагов; откат клиента безопасен, потому что кэш v1 не удаляется.

## Результаты реализации разделов 6–8 (проверка чтением кода, на устройстве не запускалось)

**6.1 Диагностика (по коду, лог устройства не снимался).**
- (4) нет перерисовки: подтверждено. До правки на `mokaBadgesChangedNotificationName` были подписаны только `ChatListItem` и `ContactsPeerItem`; ни `PeerInfoScreenNode`, ни `ChatTitleComponent.View` не слушали уведомление, поэтому экран, открытый до загрузки списка, значок не получал.
- (2) не в списке / не разработчик: подтверждено для `xdshka` и `litteraliy` (в прежнем коде их имён нет вовсе; `xdshkaaa` распознавался только по имени).
- (3) пустой значок у `xdshkaaa`: возможно, `...617` придуман и такого emoji может не быть; не проверено, заглушка оставлена по решению владельца задачи (TODO в коде).
- Подписи на iOS не было: профиль брал `CachedUserData.verification` и показывал только описание проверки бота (`PeerInfoProfileItems`), `signature` не читался нигде. Подтверждено.
- (1) данные не дошли до `MokoBadges`: по коду не определить. Теперь это видно в Console.app по категории `badges` (запрос списка: источник, статус, число записей, `rev`). Не проверено на устройстве.

**Журнал (8).** `os.Logger`, категория `badges`. По решению владельца в журнал не пишутся ни user id, ни подписи, ни URL: только источник (`api`/`github`/`bot`), статусы и коды ошибок, число записей, `rev`, тип события (`granted`/`updated`/`revoked`), `resync`. Это уже, чем в формулировке 8.1 («событие … id»): id в строке нет.

**Решения по разделу 7.**
- Серверный синий (`blue`/`blueEmojiId`) рисуем для не-разработчиков (7.7). Приоритет: клиентский синий разработчика > личный `emojiId` > серверный синий > общий `defaultEmojiId` > встроенный.
- Разработчики: id `6612638154` (владелец) и имена `ecronx` (владелец), `xdshkaaa`, `xdshka`, `litteraliy`. `xdshka` и `litteraliy` получают роль «Разработчик mokaGram» и синий значок `iconEcronx`.
- `xdshkaaa` оставлен с заглушкой `iconXdshkaaaPlaceholder` (...617) по решению владельца задачи; TODO заменить на настоящий emoji id, поэтому 7.2 закрыта не полностью.
- Подпись: роль команды > `signature` сервера > «Поддерживает mokaGram», до 64 знаков (`MokoBadges.signatureText`). Строки уже были в `desktop.inc`, новых не добавлялось.
- Профиль подставляет синтетический `PeerVerification` человеку с галочкой, кроме ботов (настоящая проверка бота не меняется). Профиль и заголовок чата перерисовываются по `mokaBadgesChangedNotificationName`.
- Карточка «о чате» (7.6) не делалась: задача открыта.
